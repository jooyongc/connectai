## 🔍 섹션 1. 법적 및 정책적 제약사항 (Legal & Policy Constraints)

| 구분 | 핵심 내용 | 리스크 레벨 | 개발 시 유의점 |
| :--- | :--- | :--- | :--- |
| **서비스 약관 위반** | Google은 자동화된 대량 데이터 크롤링(Scraping)을 강력히 금지합니다. 반드시 공식 API를 사용해야 합니다. | 🔴 매우 높음 (법적/계정 정지) | 모든 요청은 `Google Maps Platform`의 API 호출 방식으로만 처리되어야 함. 로직에 Anti-Bot 방어 및 Rate Limit 핸들링 필수. |
| **Rate Limiting** | 각 API 키는 초당/일별 호출 횟수 제한(Quota)이 존재합니다. 특히 Places Details와 같은 고가치 데이터 요청은 비용과 빈도 제약이 심함. | 🟡 중간 (운영적) | **요청 분산 로직(Distributed Request)** 구현 필수. API 호출 실패 시 대기 시간(Exponential Backoff)을 적용하여 재시도하는 시스템 설계 필요. |
| **인증 방식** | 상업적 자동화 사용을 위해서는 단순 API Key를 넘어 **OAuth 2.0 (Service Account)** 인증 방식을 사용하는 것이 가장 안전하고 확장성이 높습니다. | 🟢 낮음 (기술적) | 민감한 API 키 관리를 위한 환경 변수 및 Secret Manager(AWS Secrets Manager 등) 연동이 필수입니다. |
| **데이터 소유권** | 수집된 리뷰 데이터의 저작권은 구글에 있으나, *API를 통해 제공받는 원본 데이터를 가공하여 도출한 '평판 점수 지표' 및 '위험 비용(Risk Cost)'*은 connectai의 독자적 IP로 간주합니다. | 🟢 낮음 (비즈니스) | 서비스 약관 내에서 데이터 사용 범위를 명확히 정의하고, 아웃풋 데이터를 오직 비즈니스 분석 용도로만 제한해야 합니다. |

## 💻 섹션 2. 기술 구현 상세 가이드라인 (Technical Implementation Guide)

### 1. 핵심 사용 API 및 기능 분리
| 기능 목표 | 추천 Google API | 데이터 유형 | 난이도 기여도 | 비고 |
| :--- | :--- | :--- | :--- | :--- |
| **상점 검색/위치 파악** | Places API (Find Place) | Business ID, Lat/Lng | ★☆☆ (낮음) | 초기 리스트업 및 기본 정보 수집에 사용. 가장 비용 효율적임. |
| **세부 평판 데이터 확보** | Places Details API | 리뷰 텍스트(최신), 점수, 주소 상세 등 | ★★★ (높음) | 이 API가 핵심 데이터입니다. Rate Limit과 Cost 관리에 가장 큰 주의를 요합니다. |
| **검색 트렌드 파악** | Google Trends API (혹은 자체 키워드 분석 모듈) | 검색량 추이, 지역별 관심도 | ★★☆ (중간) | 직접적인 구글맵 데이터는 아니나, '왜' 리뷰가 생기는지 맥락적 이해를 돕습니다. |

### 2. 개발 아키텍처 개선 요구 사항
| 영역 | 현재 상태 (V2.0 초안) | 개선 필요 사항 | 기술 영향도 |
| :--- | :--- | :--- | :--- |
| **API 호출 계층** | `Data Processing Engine`에서 직접 API 호출 로직 구현 가정 | **Dedicated Proxy/Adapter Layer 도입.** 모든 Google API 통신을 이 별도의 Adapter를 거치게 하여, Rate Limit 및 인증 오류 처리를 중앙 집중화해야 합니다. | 🟢 높음 (구조적 개선) |
| **데이터 저장소** | 단순 데이터베이스 연동 가정 | `Source Data`와 `Processed Data`를 반드시 분리합니다. 원본 API 데이터를 로우(Raw)하게 보관하여, 추후 Google 정책 변경 시 재분석이 가능하도록 해야 합니다. | 🟡 중간 (운영적 개선) |
| **비용 관리** | 미반영됨 | 모든 데이터 수집/요청에 대한 **실시간 비용 카운터 및 예산 경고 시스템**을 개발 초기 단계부터 포함해야 합니다. | 🟢 높음 (재무적 안정성) |

## 💰 섹션 3. 리스크 평가 및 예상 구축 비용 (Risk & Cost Assessment)

### 1. 기술적 난이도 평가
*   **평가:** **★★★☆☆ (상)**
*   **근거:** 단순한 CRUD(Create, Read, Update, Delete)를 넘어, 외부의 복잡하고 엄격하게 통제되는 플랫폼(Google)에 의존하는 자동화 시스템을 구축해야 하므로 난이도가 높습니다. 특히 오류 처리(Error Handling), 비용 최적화, Rate Limit 회피 로직 설계가 전체 프로젝트 성공의 핵심 변수입니다.
*   **요구 개발 역량:** Python/Flask 기반 백엔드 + **클라우드 인프라(AWS/GCP)** 전문성 (API Gateway, Secret Manager 활용 경험 필수).
